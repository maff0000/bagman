#### 6.A.1.A — Mandatory correction: notification uniqueness and idempotent concurrent creation

A real PostgreSQL unique constraint on `(incident_id, purpose)` (not merely application-level deduplication) — `INITIAL`, `RECOVERY`, and `REMINDER_24H` are each singular per incident: **exactly one reminder total per incident, ever** (not a recurring daily nag — this is a deliberate, explicit clarification of PID §118.I's "one controlled reminder" language, resolved here as "one," not "one per day"). Creation must use `INSERT ... ON CONFLICT (incident_id, purpose) DO NOTHING RETURNING *`; when the `INSERT` returns no row (a concurrent creator already won), the caller must `SELECT` and return the already-existing row — **never** treat the conflict as an error, and **never** attempt a second dispatch. This must be proven by an executable concurrent-creation test (§12).

#### 6.A.1.B — Mandatory correction: reclaim, retry exhaustion, and dual-predicate fencing

The claim predicate (PID §118.E.1, refined here) must:
- Match due `PENDING`/`RETRYABLE_FAILURE` work (`next_attempt_at <= now()`) **and** expired `IN_PROGRESS` work (`claimed_at < now() - interval '<claim_timeout>'`) in one predicate, exactly as PID §118.E.1 specifies.
- **Increment `attempt_count` atomically in the same claim `UPDATE`, every time a claim succeeds — including a reclaim of an expired `IN_PROGRESS` row.** A reclaimed **claim** counts toward `max_attempts`; it is never a free/reset attempt. **Corrected exhaustion boundary (fixing a genuine off-by-one caught by Independent Audit against an earlier draft of this document — the original "to or past `max_attempts`" wording would have silently refused the final, legitimately-allowed claim):** a claim is permitted — and `attempt_count` incremented — whenever the row's **current** `attempt_count` is **strictly less than** `max_attempts` (i.e. `attempt_count < max_attempts`, checked *before* incrementing); only when `attempt_count` has already **reached** `max_attempts` (meaning every permitted claim, including the final one, has already occurred) does the row transition directly to `TERMINAL_FAILURE` instead of being claimed again. This exactly mirrors the cited precedent (`services/evidence/classification_job.py`/`ai/jobs.py`): for `max_attempts=3`, all of claim 1, 2, **and 3** are genuinely permitted to occur before exhaustion is declared, never one fewer. FORGE must implement this exact boundary and must not reintroduce the "would reach" variant.

  **Terminology correction — `max_attempts` governs work *claims*, not guaranteed external provider calls (Architect ruling, 2026-10-20).** A claim can itself be abandoned — by a worker crash — at any point after `attempt_count` is incremented but *before* the Pushover HTTP call is ever issued. **This design does not, and must not be read to, guarantee that `max_attempts=3` results in three real calls to Pushover** — it guarantees at most three *claimed work cycles*, each of which may or may not reach the point of actually calling the provider. This is a meaningful, disclosed distinction, not a weakening of the fix above: the corrected boundary still guarantees the budget is never under-spent (no claim is refused before the true budget is exhausted), while honestly declining to claim an exactly-three-provider-calls guarantee that distributed-systems reality (crash-before-send) cannot actually deliver.

  **Required test scenarios, each distinct and independently proven** (not merely implied by the fencing/reclaim tests already required above):
  1. **Ordinary three-attempt exhaustion** — no crash; each of 3 claims genuinely reaches the Pushover call, each genuinely fails (e.g. simulated 5xx), the 3rd failure's own completion write transitions the row to `TERMINAL_FAILURE` (not a 4th claim being refused — completion-time failure handling and claim-time budget-refusal are two different code paths, both must be exercised).
  2. **Crash after claim but before sending** — a claim succeeds (`attempt_count` incremented, row `IN_PROGRESS`), the simulated worker crashes before ever issuing the Pushover HTTP call; after the claim timeout, a reclaim occurs; `attempt_count` reflects the already-consumed claim, not a reset.
  3. **Crash after sending but before acknowledgement** — a claim succeeds, the simulated worker genuinely calls Pushover (a real or realistically-mocked send occurs) but crashes before writing its own completion record; after the claim timeout, a reclaim occurs and may genuinely re-send — this is the already-disclosed at-least-once risk (§118.E.2), now explicitly exercised as its own distinct test rather than only described in prose.
  4. **Reclaim with fencing** — the existing dual-predicate (`claim_generation` + `state='IN_PROGRESS'`) stale-worker-write-rejection test, confirmed to still pass independently of the above three.
  5. **No claim beyond the exhausted budget** — once `attempt_count` has genuinely reached `max_attempts` (via any combination of the above), independently prove no further claim of any kind (normal due-work pickup or reclaim) ever succeeds against that row again.

  **An exhausted (`TERMINAL_FAILURE`) notification must remain visibly failed and must never cause its parent incident to resolve.** Notification delivery outcome and incident resolution are and remain two entirely independent facts — §118.H's own per-class recovery proof (a real successful mailbox sweep, etc.) is the only thing that ever closes an incident; a `TERMINAL_FAILURE` notification leaves the incident's own `NeedsYouItem` exactly as actionable as before, since the operator can still see and act on it through the GUI regardless of whether the out-of-band nudge ever arrived.
- Apply bounded backoff via `next_attempt_at` exactly as PID §118.E already specifies.
- **Completion writes must be fenced by both `claim_generation` and current state**: `UPDATE ... WHERE notification_id=$id AND claim_generation=$my_generation AND state='IN_PROGRESS'` — the added `state='IN_PROGRESS'` predicate is defense-in-depth alongside the generation check, so a stale worker's write is rejected even in an edge case where generation alone might not have been bumped yet. A write matching zero rows is a correct, silent no-op — the stale worker must not treat this as an error requiring its own further action.
- This must be proven by executable crash/reclaim/exhaustion tests (§12) — not code inspection alone.

#### 6.A.1.C — Mandatory correction: pre-dispatch incident-state recheck and durable suppression

Before a claimed `INITIAL` or `REMINDER_24H` notification is actually sent to Pushover, the worker must re-check the parent incident's **current** `status`. If the incident has since transitioned to `RESOLVED` (recovered between notification creation/claim and actual send), the notification must be written directly to the new **`CANCELLED`** state (fenced by the same `claim_generation AND state='IN_PROGRESS'` predicate as any other completion write), with `cancellation_reason` recording the incident's resolution evidence, and a corresponding `AuditEvent` (e.g. `MAILBOX_HEALTH_NOTIFICATION_CANCELLED`) for a durable, auditable record — the external send to Pushover must **not** occur for a cancelled notification. **`RECOVERY` notifications are never subject to this check** — they exist specifically to announce the resolution and must always be sent once created, per PID §118.H/I. **This design does not, and must not pretend to, recall a notification whose state is already `ACCEPTED`** — Pushover's own API offers no retraction mechanism, and this WO does not invent one; the suppression check only ever prevents a **not-yet-sent** notification from going out after the fact. **Honestly disclosed residual gap (consistent with this WO's own disclosure discipline elsewhere, e.g. §118.E.2's "exactly-once delivery is not claimed"):** a narrow TOCTOU race remains between the recheck query returning "still OPEN" and the subsequent Pushover HTTP call itself — an incident that resolves inside that brief window will still result in a real send. This is accepted as a residual, sub-second-scale risk, not eliminated by this design, and must not be overclaimed as fully closed in any implementation report or closure document. This must be proven by executable tests covering incident resolution while a notification sits in each of `PENDING`, `RETRYABLE_FAILURE`, and `IN_PROGRESS` (§12) — these tests prove the recheck itself works, not that the narrower race window has been eliminated (it has not).

11. **`scripts/evaluate_mailbox_health.py`** (already-authorised file, extended requirement — Architect Decision D) — **`AUTH_REQUIRED` and `OAUTH_RECONNECT_INCOMPLETE` are independently observable conditions, never mutually exclusive categories.** The current trigger-detection logic uses a single `triggered_class` variable that can hold only one value per evaluation cycle — **this must be corrected** so that both failure classes are detected and, where independently evidenced, both may have their own genuinely separate `OPEN` incident simultaneously (the schema already supports this: the partial unique index is scoped per `(mailbox_id, failure_class)`, never per-mailbox alone — no migration or schema change is required for this correction).
    - **`AUTH_REQUIRED` must be evidenced by EITHER of two fully independent sources — provider-neutral, not the exclusive-source design in the prior draft of this amendment (corrected per Architect review, 2026-10-21, "authentication evidence must remain provider-neutral"):**
        1. **Live signal (pre-existing, gating corrected per Architect review, 2026-10-22)**: `detect_auth_required(mailbox)` — `mailbox.status == "ACTIVE" and mailbox.connection_state == CONNECTION_STATE_AUTH_REQUIRED` — fires **only when no OAuth-pending-state record exists for this mailbox at all** (`pending_expired is None`), exactly matching the evaluator's own pre-existing `elif pending_expired is None` branch — **unchanged from the implementation's own current behaviour, not a new restriction**. `connection_state == AUTH_REQUIRED` alone is an **overloaded** value: it is set both by a genuine confirmed failure (`mark_microsoft_auth_required`/`mark_microsoft_connection_error`-with-`AUTH_ERROR`, called with a real `error_detail`) **and** by the mere act of starting a fresh connect attempt (`begin_microsoft_connect`'s own `NOT_CONFIGURED → AUTH_REQUIRED` step, before any login outcome is known) — the two are indistinguishable from `connection_state` alone once a pending OAuth-state record exists, so source 1 must not be trusted as independent proof while **any** pending-state record exists for the mailbox, whether that record is still unexpired or has since expired. This is what correctly detects **IMAP's synchronous credential-login failure** (`mailboxes_imap.py::connect_imap` calls `mark_microsoft_auth_required` directly on a real login `AUTH_ERROR` — IMAP has no OAuth-state concept at all, so its own pending-state lookup always returns "none pending," `pending_expired` is always `None`, and this path fires immediately, exactly matching Architect requirement "a confirmed live credential failure from a non-OAuth provider, such as IMAP: `AUTH_REQUIRED` immediately") and any provider's confirmed failure through a legitimate connection lifecycle **before any reconnect has ever been initiated** (no pending-state record created yet), in the same cycle it occurs.
        2. **Durable signal (newly added by this correction)**: a qualifying `mailbox_sweep_runs` row with `error_code == SweepFailureReason.TOKEN_REFRESH_FAILED`, at or after the bound checkpoint specified below (`mailbox_sweep_runs` is append-only and requires **no new persistence**; confirmed as the real, existing enum value recorded by `services/mailbox/sweep.py` on a genuine refresh failure). This source fires **independently of the pending-OAuth-state status** — absent, expired, or still genuinely unexpired — specifically so that a later reconnect attempt, abandoned **or still genuinely in flight**, never silences already-durably-evidenced proof of a real prior failure.
        - **The `AUTH_REQUIRED` incident is created/sustained if EITHER source holds** (not both required; the partial unique index already prevents a duplicate row if both independently hold in the same cycle).
        - **Source 2's trigger is independent of `connection_state` reaching `CONNECTED`, consistent with PID §118.H's own recovery-proof principle** (Independent Audit, 2026-10-21, correctly flagged this as a real, reachable window not previously addressed): a genuine OAuth reconnect's callback-driven success (`mark_microsoft_connected`) sets `connection_state=CONNECTED` independently of any sweep completing — `record_microsoft_sweep_success` (the only call that advances the source-2 checkpoint, `mailbox.last_successful_sweep_at`) is invoked only after a sweep reaches `SUCCEEDED` (`services/mailbox/sweep.py`), and a sweep itself requires `connection_state == CONNECTED` as a precondition to even run. A pre-reconnect qualifying `TOKEN_REFRESH_FAILED` row therefore remains "at or after the checkpoint" — and source 2 correctly continues to create/reaffirm the `AUTH_REQUIRED` incident — until a sweep genuinely succeeds and advances `last_successful_sweep_at`. **This is intentional, not a defect**: it is the identical principle PID §118.H and Architect Finding A (§6.A item 2's `detect_recovery`) already establish for incident **closure** (`connection_state == CONNECTED` alone is never proof of recovery) applied consistently to incident **creation/reaffirmation** as well — a mailbox is not treated as genuinely healthy by this WO until a real ingestion succeeds, not merely until a login screen is completed. **A consciously accepted tradeoff, named explicitly here, not an overlooked one**: an operator who has just completed a visibly successful reconnect may still see the `AUTH_REQUIRED` incident/Needs-You item remain `OPEN` until the next sweep genuinely succeeds — a real, momentary operator-experience cost that incident *closure*'s own conservatism does not carry (closure delays removing an alert; this delays nothing visible being removed that wasn't already present). This WO accepts that cost in exchange for never showing a falsely-resolved state before ingestion is actually proven to work again; a future WO may revisit the UX of this specific window, but this amendment does not change it.

Independently re-confirmed by direct code inspection of `_idempotent_connection_transition` (`services/mailbox/mailbox.py`): when the mailbox's `connection_state` is **already** `AUTH_REQUIRED` (the common case — a genuine failure already recorded), calling `begin_microsoft_connect` again is an **idempotent no-op** that returns the mailbox **unchanged**, leaving any existing `last_error_code`/`last_error_detail` **untouched**. The fields are cleared only on a genuine transition **into** `AUTH_REQUIRED` **from a different** `connection_state` (e.g. `CONNECTED → AUTH_REQUIRED`), where there was no real failure evidence in those fields to lose in the first place. This correction **does not depend on that factual claim being universally true** — source 2 above is retained purely as an independent, additional corroboration for whatever cases do genuinely lose live-field evidence across state transitions; it is never a replacement for source 1, which remains fully trustworthy on its own and is the **sole** available source for providers/situations (such as IMAP) that never populate `mailbox_sweep_runs` with `TOKEN_REFRESH_FAILED` at all.
    - **Evidence bound for source 2 only — precisely specified, not left to Implementer judgment, unchanged from the previously-accepted correction** (Independent Audit, 2026-10-21, correctly flagged the original "at or after the start of the mailbox's current unresolved connection problem" wording as operationally undefined for first-time incident creation — unlike `detect_recovery`, which already has an existing incident's own `first_observed_at` to anchor against, there is no incident yet at trigger-detection time, so no symmetric anchor exists without this correction): a qualifying `TOKEN_REFRESH_FAILED` row counts as evidence **only if its `completed_at` is at or after `mailbox.last_successful_sweep_at`** (or, if the mailbox has never completed a successful sweep — `last_successful_sweep_at is None` — at or after `mailbox.created_at`). `last_successful_sweep_at` is the one field already in the existing schema that unambiguously marks the mailbox's last known-good checkpoint (stamped only by a genuine successful sweep completion, `None` at mailbox creation — confirmed via direct code read of `services/mailbox/mailbox.py`) — a `TOKEN_REFRESH_FAILED` row dated before this checkpoint belongs to a prior, already-recovered episode and **must not** be treated as evidence of a new, currently-unresolved problem. A bounded, limited-row-count query (e.g. reusing the `PERSISTENT_PROVIDER_ERROR` trigger's own `limit=`-bounded `list_runs(...)` call verbatim) does **not** satisfy this requirement and must not be used for this check — the lookback must scan sweep-run history back to the checkpoint above, however far that is, not merely the most recent N rows.
    - **Do not infer authentication failure solely from `connection_state == AUTH_REQUIRED` when that state resulted only from starting a normal OAuth reconnect flow — unexpired or since expired, with no independent credential-failure evidence** (Architect correction, 2026-10-22, closing a false-positive this amendment's prior draft did not address): source 1 fires **only when `pending_expired is None`** (no pending-state record exists for the mailbox at all); once any pending-state record exists, `pending_expired is False` (genuinely in-flight, unexpired) or `pending_expired is True` (abandoned, since expired) **both** suppress source 1 equally — a mailbox that has never yet established a genuine confirmed failure, and whose reconnect attempt is later abandoned and expires, must produce **only** `OAUTH_RECONNECT_INCOMPLETE`, never a speculative `AUTH_REQUIRED` from source 1 alone. Source 2, precisely because it is independently durably evidenced rather than speculative, is **not** gated by `pending_expired` at all (see above) — present, unexpired, or expired, a pending state of any kind never silences it, and a genuine independently-evidenced live credential failure is therefore never suppressed merely because an OAuth reconnect was initiated.
